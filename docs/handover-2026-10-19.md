## 2. The Rings + Clouds CPU question: closed

**Verdict (Tests 32-34, the user's agreement):** Rings at polyphony "all" (six voices) plus Clouds on the master does not fit this CPU at full quality. **Polyphony 4 plus Clouds works well** (the user's finding). **The manual must advise against using Rings and Clouds at the same time** (the user's instruction; `manual/modules.html` already says so on the Rings and Clouds rows).

What was measured (all on the device, `docs/device-tests.md` Tests 28-34):
- 399 MHz core; both caches 16 KB; a cache line from SDRAM costs 100-190 cycles.
- **Per audio block (1.45 ms):** Rings six voices = 50% of the period; Clouds master granular = 12% (49 MHz) alone, more next to Rings (cold caches); the firmware's own work ~25% idle, more while playing. Over 100% the audio thread **drops blocks**: 7-18% dropped in Tests 33-34. The pops, pumping and cut tails the user heard are the dropped audio, not the grain cap.
- **The firmware's block counter (`0xff8016e0`) counts processed blocks**, so dropped blocks never skip it; the probe's clock reading (cycles per counted block) went to 460-471 "MHz" when 13-18% were dropped. The governor now also watches the mean call interval over 64 calls against the nominal period (2% margin): that does see drops and gave no false trips idle.
- **ADI EE-197** (the Blackfin BF53x latency note, same core as the BF524; summary in `docs/rings-op1-reference.md`): the MAC/ALU/shifter chain has no pipeline latencies, so the mode bank's device excess (30 vs 23.7 cycles per mode-sample) was cache lines. The prefetch (two modes ahead, aligned loop tops) bought only 4%, and the user's Rings model is a string model that doesn't use the mode bank at all.
- The remaining sound-identical savings are single-digit percent. Batching two effect calls was rejected (it doubles the per-block peak). Sound-changing savings (mode budget, earlier sleep, Clouds share 0.40) were tried in Test 29 and rejected by the user.
- **Master compressor/drive (mixer page 4):** not a lever. Its four settings go to `0xff80189c`, a loader (`0x1a29d30`) converts them to floats for the Core, and the DSP runs in the encrypted L1 Core code with no bypass flag; expected cost 1-4% anyway. Notes in `docs/memory-map.md`.

Code that stays from this work (all bit-identical in the simulators): `ports/rings/src/mode_bank_bfin.S` (prefetch, aligned loop tops), `ports/clouds/src/core/governor.h` (fixed vs per-grain cost model, block-counter and interval overrun signals, share 0.70), Clouds' parameter caches, Rings' sleeping-voice skip, the probe (`ports/rings/op1/cpu_probe.cc`, `make op1-cpuprobe`), stage timers (`ports/clouds/src/core/profile.h`), `make hot-set` / `tools/hot_set.py`.

**Test 35 (proposal, not run):** confirm the polyphony limit with the probe (polyphony 4 then 2 next to master Clouds; page 0's clock should read 399, page 2's 9 ~1000). The user has effectively answered it (4 works), so it's optional.

## 3. Marbles and Grids: key transport (seq14, Test 36, awaiting the user)

The user's request: the stock behaviour, because an armed tape starts recording on the first key and everything must line up.
- **Hold a key or chord to run.** The run starts on the key press: Marbles' clock and deja vu loops restart there, Grids' bar starts there (step 1 on the press).
- **Shift while holding latches** (hold): the run continues after the keys go up.
- **The next key press takes over** (Marbles: new root in scale mode or new chord in keys mode) and clears the latch; its release stops. The last key up stops.
- Marbles: a key pressed with shift already down plays through (sounds as itself). Grids: keys no longer sound themselves (no fill-on-hold, no pass-through); an assign still auditions its key.
- Implementation: `ports/marbles/op1/marbles_seq.*` and `ports/grids/op1/grids_seq.*` (`latched_`, `restart_`, `t_offset_`, `set_shift_held`); the hosts poll the shift flag (`0x01dd7f78`) before each Tick. `sim-seq` and `sim-grids` cover it. Docs: `docs/device-tests.md` Test 36 (procedure), `docs/marbles-port.md` §9, `docs/grids-port.md` §6.5.
- The user: "the grids and marbles changes are fine for now. I need to think about the user experience for grids some more." Expect a Grids UX discussion later; don't change Grids' controls unasked.

## 4. The manual

- `manual/modules.html` (one self-contained file, light/dark): every synth engine, drum module, effect, LFO, sequencer and mixer page, stock and added, with the technique and the blue/green/white/orange knobs, shift layers and our clicks. Knob names are Teenage Engineering's (their guide PDF and the manual 1.2 reference tables); techniques combine TE's "type" lines, the firmware's source-file names from its assertion strings (phone = `Ptch.cpp`, a pitch shifter; cwo = `BodeAudioEngine.cpp`, a frequency shifter; spring = `Rymd.cpp`; nitro = `Ftwo.cpp`; dsynth shares dbox's dual-oscillator design), and what the disassembly confirms (phase = phase distortion wavetable; string = noise-burst Karplus-Strong).
